# Threat model

## Assets

1. Camera credentials (in the configuration and in source specs).
2. The video itself - live and through relays.
3. The host: a media server is one remote-code-execution away from a pivot
   into the LAN where the cameras live.
4. TURN credentials (`webrtc.ice_servers`): the relay bills the installation
   for what is relayed with them, and openIVR's user name names the site.

## Adversaries

| Who | Reaches | Wants |
|---|---|---|
| LAN host | WebRTC UDP/TCP, any port bound beyond loopback | to watch, to crash, to pivot |
| Local process / SSRF through the NVR backend | loopback API and RTSP | to reconfigure streams, read credentials, run commands |
| Compromised camera | the RTSP client, as a server | to exploit the parser, to exhaust memory |
| Remote viewer through a TURN relay | WebRTC | to watch more than allowed |
| The TURN/STUN server, or whoever can send from its address | the TURN client's socket, the shared socket | to forge answers, inject data, use our allocation |

## Threats and their controls

| Threat | Control | Verified by |
|---|---|---|
| Command execution through a source | no command-running scheme exists; FFmpeg argv from operator templates only | `SEC-007`: grep + test that `exec:` is refused |
| Admin API reached from loopback or SSRF | authentication on every call; loopback is not trusted | `SEC-001` |
| Credentials in logs, errors, `/api/streams` | `SourceSpec` displays redacted; raw only via `expose()` | `SEC-005`: property test + log capture test |
| Malformed RTSP/RTP/SDP from a camera | retina's parsers (fuzzed upstream); our own parsers fuzzed; no panic on input | `SEC-010`, `CORE-001` |
| Malformed `ANNOUNCE` body or RTP from a local process (a publisher, before its token is checked) | the SDP parser (sdp-types 0.2: 0.1 panicked on a malformed line before a session line) and retina's depacketizers, both fuzzed through our harnesses. Around retina: the losses reported to it between two frames are kept under half its 16-bit counters (large sequence gaps at one timestamp overflowed them: a panic in a debug build, a wrong count in release), and the frame cap applies to the frame that comes out (AVCC makes tiny NAL units up to five times larger than the payloads counted on the way in) | `fuzz/` targets `sdp_announce`, `depacketize`; `a_malformed_line_before_a_session_line_is_refused`, `large_sequence_gaps_never_overflow_the_loss_count`, `a_frame_over_the_cap_never_comes_out` |
| Timestamps chosen by a source (a compromised camera, a broken transcode) to overflow arithmetic or to part a stream's picture from its sound for every reader | every frame is put on the hub's timeline before a consumer sees it (D12): saturating arithmetic, never negative; a step back of more than 1 s or forward of more than 10 s beyond the wall clock between two frames is anchored again at the wall clock, no time is more than 10 s ahead of its frame's arrival (a clock run fast in smaller steps is held there), so one track can be placed at most about 10 s from another; the time never goes back while a consumer is attached | `a_restart_never_goes_back` (proptest), `a_jump_forward_inside_a_run_is_anchored_again`, `a_source_whose_clock_runs_fast_is_held_within_its_lead_of_the_wall_clock`, `ticks_and_rescaling`, `a_source_that_starts_its_timestamps_again_moves_no_reader_clock` |
| A stream that reads itself through others (`a: stream:b`, `b: stream:a`, or loopback URLs that spell it), written to make resolution loop or multiply | `Hub::upsert` refuses a stream through whose aliases one media would come back to it, under the write lock (two upserts closing one cycle cannot both pass); resolving one media enters a stream again only with another wish or from nearer the top (a fan-out of aliases onto the same streams that finds no source walked 16^8 streams with the depth bound alone), follows at most 8 aliases in a row, keeps at most 64 candidates and enters at most 256 streams, the rest passed over with a warning; an alias is never run, so it cannot republish or amplify frames | `a_stream_that_would_read_itself_through_others_is_refused`, `aliases_are_followed_up_to_a_depth`, `the_candidates_of_one_media_are_bounded`, `a_fan_out_of_aliases_that_leads_nowhere_is_resolved_in_bounded_time`, `the_streams_entered_for_one_media_are_bounded`, `sources_are_checked_when_the_stream_is_created` |
| Memory exhaustion by a camera or a viewer | every buffer bounded (`Limits`); frame size cap; GOP cache cap; backlog cap; each consumer's queue bounded in bytes (a per-item overhead counted, so a flood of tiny frames is bounded too) and in time by its class, enforced by the producer, so a consumer that stops reading holds at most its budget (32 MiB for an RTSP reader, 8 MiB otherwise, by default; the streams' and queues' sizes from the file are capped at 4096 MiB and their times at 3600 s, so a byte count or a deadline from them never overflows) of frames that are mostly shared with the others; the egresses keep no backlog of their own (an RTSP connection's write queue holds 1 MiB and one frame) | `CORE-002`, `SEC-006`, `tiny_frames_are_bounded_by_their_overhead`, `a_queue_is_bounded_by_its_bytes_too`, `a_reader_paused_beyond_its_budget_resumes_at_a_keyframe` |
| A viewer's keyframe requests (RTCP PLI, FIR) used to make the server send far more than the stream (each is answered with the cached group of pictures, up to `gop_cache_bytes`) | one replay per session per second, the requests in between answered together, and a cut of the session's own queue asks under the same interval; a session costs at most one group a second on top of its stream, and sessions are bounded (D9); a replay goes only to the session that asked, through the path ICE chose | `keyframe_requests_are_answered_at_most_once_a_second`, `a_replay_waits_for_its_interval_and_requests_meanwhile_make_one` |
| Connection floods | a total and a per-address limit on the API, RTSP and WHEP (loopback counted like any address, a global IPv6 peer by its `/64`, a link-local one by its address: D9; refusals at the total and per-address bounds, and WHEP offers refused for want of a session, are logged at most once a second, with their count, so a flood does not flood the log: `oxrtc_core::Refusals`); idle timeouts; body caps; a deadline on a whole request (below) | `SEC-006`, `the_total_limit_warns_once_per_interval_with_a_count`, `offers_refused_for_want_of_a_session_warn_once_per_interval`, `refusals_at_the_total_go_through_the_throttle`, `reaching_the_total_is_reported_once_per_interval` |
| Datagram floods on the WebRTC socket (one socket carries every session) | an oversized datagram is read whole (a 64 KiB read buffer: a smaller one made it a receive error on Windows) and a per-datagram error never pauses the loop; the kernel receive buffer is asked at 4 MiB - at the Windows default of 64 KiB a flood of 9000-byte datagrams made the kernel drop a real client's binding requests, and 3 connections in 10 failed. A datagram from a route no session knows costs one parse whatever the session count: a binding request goes to the one session whose ICE user name fragment it names, anything else is dropped (it was offered to every session in turn, each parsing it under its own lock: 48 sessions, 48 parses). Volume itself is not bounded in-process: a flood faster than the machine reads still drops packets | `oversized_junk_datagrams_do_not_stall_the_socket` (flood from its own OS thread, connection under 3 s), `an_unknown_datagram_costs_one_parse_whatever_the_session_count` |
| Slow senders (a request trickled byte by byte) | the RTSP framing examines each byte once and parses a request at most three times, so work grows with what is sent, not its square (R10); the request size cap still applies. The silence timeouts restart at every byte, so the *time* is bounded apart: an RTSP message must arrive within 10 s of its first byte (`request_timeout`, `408`), an API request's head within 10 s (`HEAD_TIMEOUT`) and its body and answer within the route's deadline (10 s, 60 s). A trickle holds one connection of its address's share for 10 s, not until the size cap | `work_stays_linear_on_a_slow_sender`, `a_request_sent_byte_by_byte_is_answered`, `a_request_trickled_one_byte_per_second_is_cut_at_its_deadline`, `the_deadline_counts_each_request_alone`, `a_request_head_trickled_one_byte_per_second_is_cut`, `the_head_deadline_spares_slow_answers_and_quiet_keep_alives`, `a_slow_answer_after_100_continue_is_not_cut` |
| SSRF through a camera URL | a source can only reach the destinations its scheme implies; the egress policy (R2) can restrict address ranges per installation | `SEC-004` |
| Header/argument injection through a spec | control characters refused at parse; FFmpeg templates split once, the input substituted as one argument | `SEC-007` |
| TURN credentials in logs, errors or printed configuration | the user name and credential never displayed (`IceServer`'s and `Credentials`' `Debug` print `***`, in the API crate's configuration too); the drivers log a server by its host and port, a refusal as "credentials refused", a malformed URL by its position, never its text; a server's reason phrase is cut to 64 printable characters | `turn_credentials_never_reach_the_log` (every event and span, every level, str0m's included, captured while one relay refuses and another relays), `debug_hides_every_secret`, `the_ice_servers_reach_the_webrtc_server_as_openivr_writes_them` |
| Forged or malformed answers from a TURN or STUN server, or a spoofer of its address (D13) | our own strict codec: a message exactly as long as its header says, at most 32 attributes, nothing after `MESSAGE-INTEGRITY` believed but a `FINGERPRINT`, fingerprints checked; a success answering a signed request must carry `MESSAGE-INTEGRITY` with the long-term key, else the request counts as unanswered; 96-bit transaction ids from the OS's random source, so an off-path sender cannot answer the requests that carry no integrity (the 401 challenge, errors); every queue and table bounded (32 requests in flight, two of them kept for the allocation's own Allocate and Refresh so that a burst of peer requests never costs it its refresh - a peer request without a place is asked for again a second later; 256 datagrams out, 128 permissions and 128 channels per allocation). Not authenticated, by the protocols' design: a STUN binding answer (at worst a wrong server-reflexive candidate, whose checks fail) and TURN's Data indications and ChannelData (what they carry still has to pass str0m's ICE, keyed by the session's ICE password, then DTLS and SRTP) | fuzz targets `turn_datagrams`, `ice_url` and their proptests (`fuzzing_tests.rs`, with a check that no timer is due right after its timeout); RFC 5769's vectors; `an_answer_without_the_key_is_not_the_servers`, `garbage_from_the_server_is_ignored`, `a_stale_nonce_is_followed_a_few_times` (three times in a row for one request; the other requests in flight when a nonce lapses are sent again with the new one without counting, `a_nonce_gone_stale_under_many_requests_costs_none_of_them`), `a_full_request_table_never_costs_the_allocation_its_refresh`, `a_peer_request_the_table_had_no_room_for_is_asked_again_soon` |
| Our allocation used as an open relay, or the relay hammered | only a session's own datagrams leave through the relay, to its own ICE peers; permissions are asked for the IPs an offer lists (at most 16 an offer, and offers come through the authenticated API, D7) and the peers str0m sends to, the least recently used one evicted beyond 128; a refused peer is asked again after a minute; at most four TURN servers; a failed allocation is retried about 1 s doubling to 60 s, refused credentials every 4 to 5 minutes, both jittered (`oxrtc_core::backoff`, as for cameras) so that the installations sharing one relay do not all come back on the same second after its outage | `permissions_are_bounded_and_the_least_used_goes`, `channels_are_bound_once_bounded_and_numbered_in_turn`, `a_refused_permission_is_that_peers_only`, `a_second_401_is_refused_credentials`, `installations_that_lost_the_same_relay_do_not_come_back_together` |
| ICE-TCP connections (a TCP listener beyond loopback, at the WebRTC port) | the total (`max_sessions`) and per-address (`max_sessions_per_ip`, D9) bounds; a connection no session claims within 10 s is closed; frames of at most 64 KiB, 256 queued per connection then dropped; a connection ends with the session that claimed it | `ice_tcp_connections_are_bounded`, `a_connection_no_session_claims_is_closed`, `a_claimed_connection_carries_frames_and_ends_with_its_session` |
| A decoder exploit in FFmpeg (a compromised camera's stream, a malformed transcode input) used to pivot into the host, read credentials, or outlive oxrtc | FFmpeg out of process (D5), argument vector, cleared environment; on Linux confined through `oxrtc-exec` (D5, R13, R29): killed with oxrtc even on `SIGKILL` (`PR_SET_PDEATHSIG`, a parent check closing the start-up race, every FFmpeg started from one thread that never ends since the signal follows the starting thread), no new privileges, address space 4 GiB / file size 0 / 256 files / no core dump / niceness +2, Landlock: read only beneath the system's binaries and libraries and the files name resolution and TLS need, so not oxrtc's configuration (unless it sits in one of those places), not `/proc/<oxrtc>/environ`, not the home or temporary directories; nothing written but `/dev/null` (truncation restricted from Linux 6.2); no signal to a process outside the sandbox (from Linux 6.12: below it a compromised FFmpeg can signal oxrtc, the same user; the startup line names what the kernel leaves out). Not covered: the network (FFmpeg can reach whatever oxrtc can, the LAN's cameras included), the system calls (no seccomp), a kernel without Landlock (warned at startup; the rest holds), Windows (job object and isolation only) | `apps/oxrtc-exec/tests/linux.rs` (every restriction read back from `/proc`, a file outside the plan unreadable, the program dead within 1 s of its parent's `SIGKILL`, nothing run when the parent is already gone), `apps/oxrtc/tests/killed.rs` (oxrtc killed, its FFmpeg gone within 1 s; on Linux `NoNewPrivs` and the limits read from the FFmpeg's `/proc`), `ffmpeg_outlives_the_thread_that_asked_for_it`, `the_secrets_are_outside_what_ffmpeg_reads`; on Linux every transcode test of `crates/ffmpeg/tests` runs FFmpeg confined. The Linux tests run in CI and on the Raspberry Pi, not on the Windows development machine |
| DTLS/SRTP weaknesses | str0m with its rust-crypto backend (aws-lc only for the certificate: D3, R15); no custom crypto | dependency audit |
| Dependency compromise | `cargo deny` (`deny.toml`: permissive licences only, RustSec advisories and yanked crates denied, crates.io the only source), `cargo audit`, pinned toolchain, `Cargo.lock` committed, CI actions pinned by commit and tools by version, a CycloneDX SBOM per release binary | `ci.yml` job `supply-chain`, `release.yml` |

## What is deliberately trusted

- The configuration file: the operator writes it. It may name FFmpeg templates.
- FFmpeg's output: it is parsed by our own depacketizers like any camera
  stream, with the same limits.
- `oxrtc-exec` beside the binary: whoever can replace it can run anything as
  oxrtc, like whoever can replace `oxrtc` itself or `ffmpeg.bin`.
